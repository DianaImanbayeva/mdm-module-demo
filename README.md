# MDM — модуль управления мастер-данными (AS Group)

Самостоятельный модуль для экосистемы AS Group, отвечающий за дедупликацию и
унификацию нормативно-справочной информации (НСИ): материалов, работ,
машин и механизмов, ресурсов, контрагентов, объектов строительства и
сотрудников. Принимает заявки на новые записи из разных систем экосистемы
(УСП, ERP, Склад, Закупки, CostCAS), автоматически сопоставляет их с уже
существующими эталонами и либо сливает совпадение, либо направляет на
ручное решение Стюарда данных.

## Возможности

- **Движок дедупликации** — нечёткое сопоставление по нескольким метрикам
  одновременно: `pg_trgm` (триграммное сходство), расстояние Левенштейна,
  Jaro-Winkler. Порог чистоты и список полей точного совпадения
  («поля унификации») настраиваются на лету для каждого типа сущности.
- **Золотые записи** — единый эталонный справочник с переводами (ru/en/ka),
  историей изменений и перекрёстными ссылками на исходные системы.
- **Очередь заявок** — новые записи со статусами `new → merged | created |
  conflict`; конфликтные позиции ждут решения Стюарда.
- **Синхронизация справочников** — массовая загрузка и сверка с ERP, а
  также подключаемые внешние источники (Склад, Закупки, CostCAS) через
  общий фоновый механизм синхронизации.
- **Ролевая модель** — Пользователь (создание заявок) и Стюард данных
  (разрешение конфликтов, прямое создание эталонов, настройка порога
  чистоты и полей унификации).
- **Мониторинг шины** — журнал событий `mdm.raw.requests` /
  `mdm.golden.updates` для интеграции с остальной экосистемой.

## Технологии

| Слой     | Стек                                                    |
| -------- | -------------------------------------------------------- |
| Backend  | Node.js, Express, JWT (SSO), PostgREST-клиент            |
| Frontend | React 18, Vite, axios, lucide-react                       |
| Данные   | Self-hosted Supabase/PostgreSQL — собственная схема `mdm`, чтение справочников из `erp` через PostgREST |

## Архитектура

Один порт (**9009**) на весь модуль: backend отдаёт `/health`, `/api/v1/...`
и статику собранного фронтенда с одного и того же адреса.

```
backend/
  supabase/*.sql             Миграции схемы "mdm"
  src/
    server.js                Точка входа: :9009, /health, /api/v1, статика frontend/dist
    config/env.js            Конфигурация из .env
    lib/
      pgrest.js               Клиент к self-hosted Supabase (PostgREST/Kong)
      erpClient.js             Чтение кандидатов на дедупликацию из схемы erp
      warehouseClient.js       Интеграция со Складом
      procurementClient.js     Интеграция с Закупками
      costcasClient.js         Интеграция с CostCAS (нормы и расценки)
      eventBus.js              Журнал шины mdm.raw.requests / mdm.golden.updates
      similarity.js, levenshtein.js, jaroWinkler.js   Метрики нечёткого сравнения
    middleware/auth.js        Проверка SSO JWT и роли "Стюард данных"
    routes/{health,mdm,erp,devAuth}.js
    services/
      matchingService.js       Движок дедупликации (пороги чистоты, unification fields)
      bulkSyncService.js       Массовая и внешняя синхронизация справочников

frontend/
  public/module.json          Контракт модуля для ERP Gateway
  src/
    App.jsx                   Общий каркас: хедер, SSO, модальное окно создания заявки
    pages/MDMPage.jsx          Дашборд, заявки, золотые записи
    components/               Детальные карточки заявки/эталона
```

## Данные и схема

Общий self-hosted Supabase — тот же инстанс, где живут схемы `erp` и
`warehouse`. MDM хранит собственные рабочие таблицы в отдельной схеме
**`mdm`** (`mdm_golden_records`, `mdm_requests`, `mdm_cross_reference`,
`mdm_audit_log`, `mdm_bus_events`), а кандидатов на дедупликацию читает из
`erp` вживую через PostgREST — без зеркалирования чужих таблиц.

Перед первым запуском в новом окружении:

1. Выполнить миграции из `backend/supabase/` в Supabase SQL Editor (создают
   схему `mdm`, таблицы и функцию `mdm.mdm_find_similar()` с `pg_trgm`).
2. Добавить `mdm` в список схем, которые видит PostgREST (`PGRST_DB_SCHEMAS`
   в конфигурации self-hosted Supabase), и перезапустить `postgrest`/`kong`.

## Запуск

Локальная разработка (два процесса, с hot-reload):

```bash
cd backend && npm install && npm run dev     # http://localhost:9009
cd frontend && npm install && npm run dev    # http://localhost:5183, проксирует /api на 9009
```

Сборка и запуск одним портом (как в `start-mdm.cmd`):

```bash
cd backend && npm install
cd frontend && npm install && npm run build   # собирает frontend/dist
cd backend && node src/server.js              # отдаёт всё с :9009
```

Перед запуском скопировать `.env.example` → `.env` в `backend/` и
`frontend/` и заполнить реальными значениями.

## Авторизация

ERP открывает модуль по ссылке вида `.../?token=<JWT>` — HS256, с
обязательными полями `sub`/`email`/`role`/`app_metadata.organization_id`.
Каждый запрос к `/api/v1/*` проверяет токен и роль; действия Стюарда
(`resolve`, прямое создание эталона, настройка порога чистоты и полей
унификации) доступны только роли `steward`/`admin`.

Для локальной разработки без реального ERP есть тестовый вход
(`POST /dev/login`, активен только при `DEV_MODE=true`).
